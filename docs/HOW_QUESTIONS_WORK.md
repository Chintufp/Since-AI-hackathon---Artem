# How a question is formed, who gets it, and what "learning" means here

**For Artem · 7 November 2026 · read from the code on the run branch and checked by three adversarial review agents against the code and the demo database (six corrections applied) (`src/libs/utils/investigation`, `questions`, `policies`, `models/testing/simulator.ts`, `experiments/runners-learning.ts`)**

The short answer to "how does the LLM form the questions": it doesn't. There is no language model anywhere in the running product. A question is a hole in a decision, found by rules; its wording is a template; the person is chosen by who has firsthand knowledge or whose role can observe the fact; hard rules cap the burden; a contextual bandit *can* choose which (question, person) pair to ask first, but it is evaluated offline and switched off. Every piece below names the file that does it.

## 1. From a pasted problem to a recommendation (before any question exists)

1. **Problem text → conditions** (`investigation/problem-parser.ts`). A lexicon of regular expressions turns phrases into typed conditions: "link is up" → `interface.status = up`; "counters are zero" or "zero counters" → `traffic.counters = zero` (note: the query-time rule does not match "counters basically zero"; the import-side extractor in `memory/extraction-config.ts` is broader and does); "older unit" → `unit.age = older`; "installed 2018" → `unit.installed_year = 2018`, which folds into `unit.age = older` for years up to 2019 (marked *inferred*); "changed the SFP" → `component.replaced = sfp`; "barrier" → `site.access = barrier`. A separate small model-name parser catches "an N5 unit" / "model N5" → `unit.model`. Any other phrasing produces nothing.
2. **Retrieval → candidate cases** (`retrieval/`): BM25 over case text, exact asset-id match, hashed character-trigram vectors, fused by reciprocal rank. Each candidate is compared condition by condition with the problem: `matchingConditions`, `conflictingConditions`, `missingConditions` (the case has it, the problem does not say; for the configured `problemStated` keys, by default `unit.model`, also the reverse: the problem states a model and the case records none, which becomes a question about the earlier unit).
3. **Two separate verdicts per candidate** (`investigation/assessor.ts`, `case-facts.ts`):
   - **Support**: did the case's own corrective action have a reported recovery? `supported` / `weak` (performed, no outcome) / `contradicted` (no-change, worse, recurred) / `unknown`.
   - **Applicability**, from the condition comparison only: a conflict on a *distinguishing* key → `inapplicable`; a distinguishing key missing, a conflict on a non-distinguishing key, or nothing matched at all → `qualified`; no conflicts, no missing distinguishing key and at least one matching condition → `applicable`. The distinguishing keys are configuration (`investigation/settings.ts`): `unit.age`, `unit.model`, `unit.revision`, `software.version`.
4. **Recommendation** (`investigation/recommend.ts`) is a decision table over (support, applicability, which attempts the case has). Wording never changes the gate.
   - inapplicable or contradicted → `retain-uncertainty`: *"Don't reuse the fix from TRN-042: older unit there, newer unit here."*
   - supported + applicable, and the case has a diagnostic check → `check-first`: *"Check the traffic counters before replacing the SFP again."*
   - supported + applicable, no diagnostic check → `reuse`: *"Consider disabling and re-enabling the interface; it reportedly restored traffic in TRN-042."*
   - supported + qualified → `qualified`: *"Confirm the unit details (older unit) before disabling and re-enabling the interface."*
   - any case with a diagnostic check and support weak or supported → a lower-ranked `check-first` ("Check the traffic counters first. The interface reset has no reported recovery in TRN-042.")
   - otherwise `none`. An action the problem says was already done is never recommended again.

## 2. Where a question comes from: gaps

`investigation/gaps.ts` looks at the hypothesis the recommendation depends on and lists what is unknown and would change the verdict:

- Each **missing distinguishing condition** is a gap with `consequential: true` and a sentence saying what each answer changes ("If older unit holds here, the response from TRN-042 becomes applicable (currently qualified); if it does not, it becomes inapplicable and the recommendation reverts to retaining uncertainty"). Two exceptions: a condition that is *hedged in its source* ("installed around 2019 I think") never creates a gap, and a condition the **requester can observe themselves** (`requesterObservableKeys`: interface status, optical level, traffic counters, traffic state, alarms, power, temperature, BGP session) becomes "check this yourself" and never becomes a question to a colleague (decision R15).
- A corrective action that was **performed but has no recorded recovery** is a consequential *outcome* gap.
- A recovery whose **lasting** effect is unknown is a gap that is explicitly *not* consequential: it would not change today's action, so nobody is interrupted for it.

So on the TRN-301 problem ("not sure which unit generation this is"), the case TRN-042 is supported, its fix depends on `unit.age = older`, the problem does not state it, the requester cannot see it, hence one consequential gap, `unit.age` (plus the non-consequential "lasting unknown" gap, which never becomes a question).

## 3. Wording: templates, never free text

`questions/generator-templates.ts` turns each open consequential gap into a `QuestionCandidate`:

- Condition gaps use a per-key template from settings: `unit.age` → "Is {asset} {a_value} unit?" → **"Is TRN-301 an older unit?"**; `unit.model` → "Is {asset} the {value} model?"; `software.version` → "Is {asset} running software version {value}?". If a slot is unknown, the generic "Is this true for {asset}: {label}?" is used instead; a question is never rendered with an empty slot (a test scans every text for "undefined", double spaces and empty parentheses).
- Outcome gaps: "Did {phrase} right after {action} on {case}?" → **"Did traffic return right after the interface reset on TRN-042?"**
- The asset is the one the *problem* names (an unknown token like TRN-301 counts as the current asset), never an asset that only belongs to the cited case.
- Each candidate carries a rationale ("Hypothesis … from TRN-042 applies only if older unit"), the two consequences `{yes, no}` taken from the gap, a `dedupKey` (gap key + entity scope) and the list of candidate recipients. Everything is built from the case *as the requester may see it* (`retrieval/access.ts`), so no hidden evidence leaks into a question.
- Answer type is always yes / no / unknown. An optional *evaluative* pair ("which of these two questions is more useful first?") exists behind a setting, is never mandatory and never becomes factual evidence.

## 4. Who is asked: question-dependent recipients, then hard gates

`questions/recipients.ts` never uses a global "expert" list:

- Outcome questions go to people with **firsthand links on that case** (performed the action, reported the outcome, advised).
- Condition questions go to people with firsthand links to the **problem's entities**, plus people whose directory **role or group is configured to observe that key** (the organisation's observability policy in `org-config.ts`: a Network Expert may observe `unit.age`). The requester is always excluded. Firsthand people sort first.

`questions/eligibility.ts` then applies the hard rules to every (question, person) pair, and only `eligible` pairs go further: `self`, `access` (the person must be allowed to see the cited case), `unavailable`, `not-answerable`, `budget` (3 per person per day, 1 open at a time, 3 per investigation), `cooldown` (30 minutes after that person's last delivered question; 24 hours before the same question, by dedupKey, is put to the same person again), `already-asked`, `duplicate` (same dedupKey), `gap-resolved`. No selector can override these; they run before it.

## 5. The selector: which pair first, or nobody

`questions/coordinator.ts` hands the eligible pairs and their visible features to a `Selector`.

- **Rules baseline (shipped)** (`policies/rules-selector.ts`): `score = consequential × (firsthand ? 1 : 0.6) × 1 / (1 + open questions of that person) × recency`; defer when the best score is below 0.2; ties break by id string order (which is why Erkki wins on the seeded directory, his entity id sorting lowest among the six role-eligible people, and may lose once more NOC people exist; open question U26 on the demo-mode branch).
- The decision is stored as a `PolicyDecision` (eligible set, chosen pair or `defer`, features, propensity, reason) and an `EvaluationRecord`. The question becomes a `QuestionRecord`: `queued` → `delivered` after an eligibility re-check → `answered` / `deferred` / `dismissed` / `cancelled`.

## 6. What an answer does

(`questions/coordinator.ts`, `investigation/investigate.ts`) Every answer is stored as its own attributed evidence record. **Yes** on a condition question becomes an observation on the current asset with the reserved value "the case's condition holds here" (`unit.age eq __answer:matches-case`, shown as "Older unit: yes (answered)"; the literal value is never copied) → applicability turns `applicable` → the recommendation is re-planned → `check-first`. **No** stores the marker "differs from the case", which the condition comparison reads as a conflict on that distinguishing key → `inapplicable` → `retain-uncertainty` ("Don't reuse the fix from TRN-042: older unit there, …", with the caveat "TRN-042 does not apply to this unit, going by the answer you received"). No `neq` operator is written anywhere. **Not sure** records no fact; the gap stays open and that person is not asked the same thing again. **Later** and **Dismiss** keep receipts and Undo; Undo withdraws the answer cleanly. Historical claims are never mutated: the answer is applied at assessment time, next to the case. An observation that resolves the gap (the requester finds the unit age themselves) cancels the queued or delivered question.

## 7. Where "RL" comes in, honestly

- It is not sequential reinforcement learning. It is a **contextual bandit**, LinUCB (`policies/linucb.ts`): one shared linear model over seven visible features of each (question, person) pair plus a bias: `consequential`, `firsthand`, `recipientOpenQuestions`, `recipientAskedToday`, `candidateCount`, `gapDecidesApplicability`, `hypothesisSupportLevel` (the coordinator also computes `recency`, which the rules selector uses and the bandit drops). It picks the pair with the highest `mean + alpha × uncertainty` (optimistic exploration, deterministic, alpha 0.5) and updates its ridge-regression state from `EvaluationRecord`s whose `assessedBenefit` is known. The reward in the family arm is **1** when the answer moved the recommendation to the class the hidden key expects, **0** when an answer changed nothing, and **null** when nobody answered; in the simulator it is 1 when a definite answer equals the hidden truth and the gap decides applicability, else 0, null when unanswered. The learning update skips null (never counts it as zero); the simulator's headline mean benefit does count unanswered and deferred steps as zero, which is part of why the rules selector, which deferred 58 times in 900 steps, scores lower there.
- Hidden truth never reaches the features; the bandit only ever sees what the product sees.
- **Where it was trained and tested**: only in experiments (E03, `experiments/runners-learning.ts`). (a) A simulator (`models/testing/simulator.ts`) with six simulated people who have hidden knowledge, responsiveness 0.55–0.95, and 0.92 / 0.7 correctness for firsthand vs hearsay; 300 steps, 3 seeds. LinUCB reached about 0.44 mean benefit against 0.34 for the rules (+0.08 to +0.14 on every seed, zero ineligible selections). (b) The "family arm" on the synthetic scenario families with the benefit labelled against the hidden answer key: **no selector asked a single validation question**, so the shipping rule (bandit beats rules by at least 0.05 on all three seeds, with zero hard-rule violations) could not be tested, and the rules stay the default. The artifacts in `data/models/linucb-e03-seed*.json` were updated from exactly four labelled questions, all with benefit 0, so their weight vector is zero: they are saved, not meaningfully trained. And `selectorId: 'linucb'` in the coordinator settings constructs a *fresh, untrained* LinUCB (the app never loads the artifacts), which ranks pairs by the exploration bonus alone.
- **In the live app nothing learns online**: the coordinator writes every `EvaluationRecord` with `assessedBenefit: null` and never calls `selector.update`. Turning real answers into a reward would need a rule for "did the answer change the recommendation, and did the engineer's later outcome report confirm it" (open question U04). Points for contributions are a separate record and never feed any reward (R11).
- Two more learned things exist and are also not in the loop: a hashed logistic "usefulness" classifier for evidence records (validation 26/32 vs majority 25/32, saved, not wired), and a recorded Claude subagent used once in E01 as a comparison arm for extraction, never as an application route.

## 8. What to say when a judge asks

"Questions are not generated by a model. A question is the hole in a decision: when a past case's fix depends on a condition we cannot see on the current unit, that condition is the question, worded by a template and sent to someone with firsthand knowledge or a role that can observe it. Hard rules cap the burden at three a day. A contextual bandit can choose which pair to ask first; it beat the rules in a simulator and we kept it off because our synthetic data never produced enough questions to prove it. Every question shows its reasoning: 'Why this question?' is the hypothesis and what each answer changes."

## 9. The real weak point, and where a model would fit

The lexicons decide what counts as a condition, both at import (`memory/extractor-rules.ts`) and at query time (`problem-parser.ts`). A paraphrase outside them produces no condition, so no match, no gap, no question. The four distinguishing keys are hand-configured. In E01 a recorded Claude pass found eleven claims the rules missed. The right place for a model, local or not, is exactly there: proposing claims and conditions in the same contract, with the gates, templates, recipients and budgets unchanged.

## 10. How evidence and "solutions" are stored (the shape of the memory)

Storage is one SQLite file, `data/local/knowledge-twin.sqlite` (`memory/sqlite-store.ts`): one table per record type (`r_evidence`, `r_claim`, `r_case`, `r_attempt`, `r_outcome`, `r_personLink`, `r_entity`, `r_investigation`, `r_question`, `r_decision`, `r_answer`, `r_observation`, `r_correction`, …), each row an id plus a JSON document plus an insertion sequence, and a full-text index (`search_fts`) for BM25. The seeded demo database holds 67 evidence records, 108 claims, 6 cases, 9 attempts, 7 outcomes, 61 person links and 28 entities. There is no field called "solution": a fix is something you *derive* from attempts and outcomes, which is why the UI can say "Reported once; cause and lasting effect not verified.". The layers, with the real TRN-042 rows:

1. **Evidence** (`EvidenceEnvelope`, `contracts/evidence.ts`): the message exactly as it was, never edited. Message 8 of the Teams thread is stored as `provider: teams`, `connectionId: import:teams:file`, `sourceId: teams:…#8`, `kind: message`, the verbatim text "That's it.⏎Disable the interface, wait a little, then enable it again. Don't reboot the whole unit unless that fails.", `author` Erkki Expert (role Network Expert, provider teams), `eventTime {known: false, raw: "09:22", sequence: 8, partial: "time-only"}` (the thread has times but no date, and that is kept as unknown rather than guessed), `thread {threadId, position: 8}`, `accessScope {visibility: org}`, `lineage {importBatchId, sourceFingerprint}` and a `reference` pointing back to the file and message number (`#seq=8`). The id is deterministic from (org, provider, connection, source id, revision), so importing the same file a second time into a live store inserts nothing ("seen 12, inserted 0, unchangedDuplicates 12"); the demo reset clears the store first, which is why it prints "seen 12, inserted 12" every time.
2. **Claim** (`contracts/memory.ts`): one typed statement cut out of one evidence span. TRN-042 produced 27 claims: 4 observations, 8 conditions, 6 hypotheses, 6 advice, 2 actions, 1 outcome. Each has `type`, `statement`, `subjectEntityIds` (the asset), `caseId`, `assertedBy` (person, role, provider), `origin` (`reported` or `inferred`), `supporting: [{evidenceId, span {start, end}, excerpt}]`, `contradicting: []`, `validity {from}`, `status: provisional` (26 of the 27; the `interface.status = up` condition is `supported` at revision 2 because two separate messages support it), `extraction {route: rules, version: rules-extractor@1}`, `revision`, and, when it expresses a condition, a structured `condition {key, operator, value, label}`. Examples: hypothesis *"Sometimes after changing the SFP the interface comes up normally, but the forwarding state doesn't recover correctly."* (Erkki, 09:18); advice *"Check whether the traffic counters are actually increasing."* (Erkki, 09:19) and *"Disable the interface, wait a little, then enable it again."* (Erkki, 09:22); action *"Veikko changed the SFP on transmission node TRN-042"* with `condition {key: action.performed, value: sfp.replace}`; outcome *"Traffic is back 👍 after the interface disabling"* (Veikko, 09:25).
3. **Case** (`Case`): the incident container. `title: "TRN-042 · no traffic after SFP change"`, `status: reported-recovered`, `entityIds` (the asset), `observationClaimIds` and `hypothesisClaimIds` (advice, action and outcome claims are reached through attempts and outcomes, conditions through `conditions`), `attemptIds` (3), `outcomeIds` (1), `evidenceIds` (13: the twelve messages and the e-mail, which joined the same case instead of becoming a second case or a second confirmation; the outcome count stays one), `startedAt` (time-only), and `conditions`: eight structured conditions each with its evidence span, `component.replaced = sfp`, `interface.status = up`, `alarms.state = cleared`, `traffic.state = absent`, `unit.age = older` (from "Yes, installed around 2019 I think."), `unit.installed_year = 2019`, `optical.level = normal`, `traffic.counters = zero`. The case also carries its own `gaps` (lasting effect unknown, cause not verified, the result of the SFP replacement and of the counter check not reported, and a non-consequential one: the date of the outcome is unknown).
4. **Attempt** (`Attempt`): what was tried, by whom, on whose advice. TRN-042 has three: `sfp.replace` (performed by Veikko, 09:14, no outcome), `counters.check` (advised by Erkki, `adviceClaimId` points to the advice claim, performed by Veikko, 09:21) and `interface.reset` (advised by Erkki at 09:22, performed by Veikko at 09:25, `performed: reported`, evidence "Disable the interface…" and "Did that."). `performed` is `reported` when an action claim or a later performed-check link exists, otherwise `proposed-only` (the type also allows `unknown`, which the builder never produces). Only advice that maps to a known action name and is not negated becomes an attempt: "Don't reboot the whole unit unless that fails" yields no attempt row.
5. **Outcome** (`Outcome`): the result after an attempt. One row: `attemptId` → the interface reset, `reportedBy` Veikko, `result: recovered`, `lasting: unknown`, `basis: reported` (a person said so; `observed` would mean a system confirmed it), evidence "Traffic is back 👍". A later message saying the problem came back sets this outcome's `lasting` to `recurred` and flips the case status. Evidence and claims are never overwritten; attempt and outcome rows are *derived* and rebuilt from the claims on every rebuild.
6. **Person links** (`PersonWorkLink`): person ↔ claim or case with a `contribution` (`reported-problem`, `advised`, `performed-check`, `performed-action`, `reported-outcome`, `observed-condition`, `mentioned`) and a `firsthand` flag. TRN-042 has Erkki `advised` (four links, one from the e-mail) and Veikko `performed-action`, `performed-check`, `observed-condition`, `reported-problem`, `reported-outcome`. These rows are what "People with relevant experience" and the recipient logic read.
7. **Entity** (`Entity`): `TRN-042`, type asset, with `attributes` that keep their origin and evidence (`unit.age: older, origin reported`, `unit.installed_year: 2019`), so an inferred value never looks like a reported one.
8. **Investigation** (`InvestigationState`): every query is stored too: the problem text and requester, the candidate cases with matching, conflicting and missing conditions, the hypotheses with their support and applicability (for the TRN-088 problem: two supported and applicable, one from TRN-042 and one from the similar TRN-117 case, one contradicted from RBS-310, one weak and qualified from RTR-117), the gaps, the recommendation with its basis evidence refs and caveats, the people, question and decision ids, the trace events and the routes used.
9. **Answers, observations, corrections** are their own records. An answer never edits a claim; it is attributed evidence applied at assessment time, so Undo is a clean withdrawal. A correction can retract or contradict a claim or link, and the case is rebuilt from what remains.

So "the solution to TRN-042" is not a sentence in a database. It is: an advice claim by Erkki at 09:22 with its span, an attempt that links that advice to Veikko's "Did that." at 09:25, an outcome row that says recovered, reported, lasting unknown, and the condition rows that say when it applied. The recommendation text is composed from those rows at query time, which is why it can be rephrased, qualified or withdrawn without touching the memory.
