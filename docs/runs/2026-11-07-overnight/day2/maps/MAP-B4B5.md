## Data flow today

B4 D1 today: nothing in the UI sends text for capture. Panel input -> submit() -> api.investigate({text, attachmentNames}) -> POST /investigate -> Engine.investigate (a question to investigate, not a thing to remember). Dropped/pasted files only add chips (names). POST /import exists over HTTP with formats teams-json, email-text, slack-export, slack-live, scenario-dir (path or inline payload); 'paste' exists in memory/index.ts ImportFormat and parsePaste but is rejected by importSchema and absent from ImportRequest. Path of an import: http.ts 'POST /import' -> parse(importSchema) -> Engine.importData -> memory/index.ts importFromPath -> importOne (adapter) -> ingest/import.ts importSources (stable ids, duplicates, copy lineage, relink) -> context/loadContexts -> memory/extractor-rules.ts extractFromContext (config: extraction-config.ts) -> assignEpisodes -> memory/commit.ts commitProposal (claims, entities, cases via case-builder, attempts, outcomes, person links) -> applyMembershipGrants -> refreshClaimSupport -> ImportResponse {batch{counts seen/inserted/unchangedDuplicates/revised/copies}, cases, claims, entities, people}; engine then reapplies directory (applyDirectory) and writes trace 'import.completed'. A pasted Teams thread through the current paste adapter would be ONE 'note' envelope (no speakers, unknown time), so D1 needs a thread/e-mail sniffer before the adapter.

B4 D2 today: scripts/slack-demo.ts --live -> checkLiveGuard (KT_SLACK_LIVE=1, KT_SLACK_TOKEN, --workspace, --channel) -> slackWebClient(token) -> pullChannelReadOnly (auth.test team match, list/info, members, users.list, ONE conversations.history, oldest-first) -> SlackExportData -> POST /import {format:'slack-live', payload, connectionId:'slack-live:<teamId>'} -> mapSlackMessage ids '<channelId>:<ts>' (so repeated pulls are idempotent) -> same pipeline. One shot, no loop, no thread replies (conversations.replies is not allowed), no incremental 'oldest' parameter, nothing posted.

Questions today: investigate -> gaps (gaps.ts) -> QuestionCoordinator.request (generate templated candidate, eligibility, selector, QuestionRecord 'queued') -> deliver() flips to 'delivered' (store only) -> recipient's panel polls GET /questions?personEntityId=… (default statuses queued, delivered, deferred) -> POST /questions/:id/answer {principal, value yes|no|unknown} -> Engine.answer: recipientCheck (directory.resolve(principal.id) === q.personEntityId, resolution works through person.actorIds such as 'person:slack:U102'), undo-if-deferred, idempotent same value, 409 on a different value, coordinator.answer (Answer record, attributed evidence text 'Answer "yes" to: <question> (answered by <name>)', Observation with ANSWER_MATCHES_CASE/ANSWER_DIFFERS_FROM_CASE for condition gaps or outcome.result for outcome gaps, investigation rebuild, cancelObsolete), points award, receipt. A Slack DM is therefore a pusher over GET /questions (delivered, not yet DM'd) and a puller of reactions that calls the same POST. Principal for a Slack user = {id:'person:slack:<U…>', displayName, groups:[], type:'human'}; Engine.effective() clamps groups to the directory person's. The person must exist in the store with that actorId (people.json actorIds or an inline ImportRequest.directory, which applyDirectory merges by actorId or normalized name onto the entity already created from the Teams/e-mail import, e.g. 'Erkki Expert').

B5 today (verified with two spikes against an in-memory Engine, optic-forwarding-a + an inline 5-message Helmi thread, requester Tapio Lehto): (1) With no change, 'the 2021 batch' is parsed nowhere, so the Helmi case (TRN-512, attempts sfp.replace and table.clear, both 'reported', outcome recovered) has no distinguishing condition: both hypotheses are supported+applicable, recommendation 'reuse' ('Consider clearing the table; it reportedly helped in TRN-512'), no gap, no question. The generic verb lexicon already derives the action 'table.clear' from 'Clear the forwarding table' (phrase falls back to 'the table clear'). (2) With a unit.batch parser (extraction-config) + lexicon rule (problem-parser) + distinguishingKeys entry + conditionTemplate + observability entry, the problem 'Replaced the SFP on TRN-577 ... Not sure which batch this unit is from' gives state.hypotheses [TRN-117 older-units, supported/qualified], [TRN-512 forwarding table, supported/qualified], ONE gap (missing unit.batch of TRN-512), question 'Is TRN-577 from the 2021 batch?' with why 'Hypothesis "Clear the forwarding table instead." from TRN-512 applies only if 2021 batch', people list containing both Aarne Koskela and Helmi Virtanen. (3) BUT a generic unit.batch regex also matched Helmi's old TRN-117 sentence 'Is this one from the 2019 batch?' so TRN-117 gained unit.batch=2019; answer markers are per KEY (investigate.ts mergeConditions stores '<key>#answer'; compareConditions.problemFor lets an answer outrank every case on that key), so a No made BOTH cases inapplicable (retain-uncertainty) and a Yes would have marked the 2019 case applicable too: the branch is not picked, it is flattened. (4) Restricting the batch pattern to 202x (or any rule that leaves TRN-117 without unit.batch) gives per-case keys: Yes -> TRN-512 applicable (reuse 'Consider clearing the table...'); in that run TRN-117 was 'applicable' because the synthetic TRN-117 case records no unit.age/revision condition ('2019 batch' and 'revision A' are not parsed by the lexicons), so there was no second qualified hypothesis. A real two-qualified setup needs expert A's case to carry a distinguishing condition (Elisa's TRN-042 does: unit.age=older from 'Is this one of the older units?' / 'Yes, installed around 2019 I think.'; synthetic TRN-117 does not). (5) Selection: recommend() ranks by rank then candidate.score; with equal rank (both qualified, 4) the higher retrieval score is `selected`, gaps and the single question are built only for it; the other hypothesis stays in state.hypotheses and matches but not in the headline. Who is asked is decided by recipients.ts: no firsthand people exist for the unresolved asset, so only ObservabilityPolicy (org-config.ts) matters.
