# Phase 1 map · B1 · Engine: validity and supersession on Claim, point-in-time `at`, access facts through the investigation, quiet hours on the demo clock, generated follow-ups in data/demo/followups/, standing gaps at commit time (missing-symptom, outcome-after-24h, pairing)

## Data flow today

IMPORT (Engine.importData -> memory/index.ts importFromPath): connectors (teams-json.ts parseTimeRef(m.time, seq); email-text.ts parseTimeRef(Date header)) -> ingest importSources -> context loadContexts -> extractor-rules.ts extractFromContext (per sentence: aside, composite outcome, yes-answer, question, 1. access-fact cue -> type 'access-fact' condition site.access=<kind>, 2. advice, hypothesis, actions, outcomes, 7. conditions via cfg.conditionParsers, 8. observations) -> episodes.ts assignEpisodes -> commit.ts commitProposal: entities upsert; claims keyed stableId('claim', orgId, incidentKey or '-', type, idBasis) where idBasis is condition key|op|value for condition/action claims else the normalised statement; NEW claim gets validity: { from: timeOf(pc.evidence) } = eventTime of the claim's FIRST evidence (Elisa thread: {known:false, raw:'09:22', sequence:8, partial:'time-only'}; Elisa email has no Date header -> unknown; remote-power-access email: known 2026-08-20T06:12:00Z; Slack: known from ts). validity.to/condition are never set; an existing claim keeps its original validity on merge. Case-bound types are observation|hypothesis|advice|action|outcome|condition only; access-fact/identity/other claims are caseless (caseId undefined). Then rebuildCase(case-builder.ts) derives attempts/outcomes/status/conditions/gaps from live (provisional|supported) claims.

INVESTIGATE (Engine.investigate -> investigation/investigate.ts investigate): parseProblemText (DEFAULT_LEXICON; site-access rule gives site.access=barrier, an ignored key) -> priorAnswerConditions -> mergeConditions -> HybridRetriever.search (retrieval/corpus.ts buildCorpus: cases only, text = title + ALL caseful claim statements regardless of status + case.conditions labels) -> visibleCandidates -> buildHypothesis -> RulesAssessor.assess (applicabilityFor + supportFor(loadCaseFacts)) -> isRelatedCandidate -> recommend -> buildGaps (missing distinguishing keys, outcome, lasting) -> buildPeople -> loop status; store.put('investigation'). Then (unless allowQuestions === false) QuestionCoordinator.request.

QUEUED vs DELIVERED today (questions/coordinator.ts request): if any queued/delivered question exists for the investigation -> return it (loop 'question-open'). Else TemplateQuestionGenerator.generate -> findRecipients per gap -> evaluateEligibility per (candidate, person) -> selector.select -> PolicyDecision/EvaluationRecord stored -> QuestionRecord created with status 'queued', createdAt=now -> `if (opts.deliver !== false) question = await this.deliver(question.id)`. deliver(): only from 'queued'; re-runs evaluateEligibility with ignoreQuestionIds [q.id]; ineligible -> 'cancelled' (gap-resolved|duplicate|obsolete); else 'delivered' with deliveredAt = now. Only questions.test.ts passes deliver:false; Engine and experiments/harness always deliver immediately. There is no timer or later delivery pass anywhere.

ANSWER -> EVIDENCE (Engine.answer -> coordinator.answer): recipient check; evidenceFor() writes an EvidenceEnvelope id stableId('ev', orgId, 'paste', 'answer:desktop', answerId, '1'), provider 'paste', kind 'observation', text 'Answer "<v>" to: <question> (answered by <name>)', eventTime {known:true, iso: clock now}, thread {threadId: investigation id}, accessScope = cited case scope or the answerer's groups, metadata {questionId, value}; Answer record (claimUpdates note support/contradict on the target claim, never mutating it); for a 'missing' gap a yes/no becomes Observation {key, eq, '__answer:matches-case' | '__answer:differs-from-case'} and for an 'outcome' gap OUTCOME_KEY eq recovered|no-change, investigationId + caseId; question -> 'answered'; rebuild() re-runs investigate with previous state so mergeConditions/loadCaseFacts apply the observation; cancelObsolete. Engine then awards points. Undo deletes answer, observation and evidence.

DEMO CLOCK now() is read at: Engine constructor (this.clock = opts.clock ?? demoClock.now) -> Engine.now() (trace at, importData `now` -> ingestedAt/claim createdAt/updatedAt, problem.createdAt, outcome reports, preferences, contact drafts, participation awards); wiring(): createSelector({rules:{clock}, epsilon:{clock}}) (linucb/ranker get no clock and use wall time), TemplateQuestionGenerator ctx.clock, QuestionCoordinator ctx.clock (request createdAt, deliver deliveredAt, answer evidence time, eligibility now, budget sameUtcDay, cooldown); investigate deps.clock (state createdAt/updatedAt, buildPeople now -> askable). clockStatus()/setClock() expose and move it (409 when opts.clock fixed). Direct wall-clock reads that bypass it: commit.ts:48 fallback, case-builder.ts:280 fallback, memory/index.ts:139 batch finishedAt, ingest/import.ts:141, connectors/types.ts:61 ingestedAt fallback.

WHERE TimeRef COMPARISONS HAPPEN / COULD HAPPEN: case-builder evidenceOrder uses compareTime (sequence fallback when either side unknown) and comparable() (same thread or both known); recurrenceReportedLater and episodes use Date.parse only on known iso; budget/eligibility compare ISO strings of question records. A point-in-time `at` filter would compare validity.from/to and evidence eventTime with `at`: the whole Elisa TRN-042 thread and its email are known:false (time-only/no date), the remote-power-access Teams thread is time-only but its case.startedAt is the email's known 20 Aug date (the email joined case 1), the follow-ups would be known (ISO with zone). compareTime cannot order a known 14 Oct follow-up against a time-only 09:22 message (falls back to sequence, follow-up seq likely 1 vs 8).

## Gotchas

- validity.from is written only when the claim is first created (commit.ts:160, `prev ?? {...}`); later supporting evidence never moves it, and it is the FIRST evidence's eventTime, so the Elisa claims all have known:false time-only from. Any `at` filter must treat an unknown from as 'valid from before any dated moment' (else the whole TRN-042 case vanishes for every `at`).
- compareTime() only compares when both TimeRefs are known; otherwise it compares `sequence` (undefined -> 0). Do not use it to decide 'newer' for supersession between a dated follow-up and an undated thread; use known iso when present, else ingestion order (claim.createdAt / importBatch order) with an explicit rule.
- Probed with the current rules (no code changes): the brief's follow-up wording 'Update on the SFP thing: the 4.2 firmware fixes the forwarding-state bug. Units already on 4.2 shouldn't see it; ...' extracts ZERO claims, with or without 'TRN-042' in the text; the software.version parser needs 'firmware 4.2' (keyword before number), not '4.2 firmware'. A variant 'TRN-042: we are on firmware 4.2 now, so the forwarding-state bug is fixed' yields an OUTCOME claim (cue 'fixed' in outcomeRecovered/states.recovered) plus condition software.version=4.2, which would wrongly add a recovery to TRN-042. Supersession cues must be checked before outcome classification, and the generated text must name the asset (or a subject line) to reach the TRN-042 case/subject.
- Access-fact condition values are the access KIND, not the code: both 'Road barrier code: 5802.' (20 Aug) and 'Barrier code at RBS-310 is now 7731 (landlord changed the lock).' get site.access eq 'barrier' (probed), so rule (a) 'same type, subject, condition key, different value' never fires for the barrier code. Either extract a code key (e.g. site.access_code = 5802/7731) or let the explicit cues ('now', 'new code since', 'changed the lock') close the older same-kind access fact.
- In email-01 'The landlord changes it every October...' is a separate sentence with no access cue and produces no claim; 'I am on leave from 3 November to 1 December.' and 'Pirkko does not handle access codes' produce no claim either (`(?:door|gate|access)\s+code\b` does not match 'codes'). The 'every October' and 'until 1 December' cues therefore need message-level (not sentence-level) handling to land on the barrier-code claim / on Eino's availability.
- False access fact in the same family: Slack 'Reminder that the van service is booked for Friday, please leave keys at the front desk.' becomes an access-fact with value 'contact' and no subject entity; an entity-bound retrieval must require subjectEntityIds to include the site.
- Access-fact claims are caseless (CASE_TYPES excludes them) so buildCorpus/HybridRetriever never see them; access-fact retrieval must be a separate lookup by subject entity (resolveEntityIds on the problem text), filtered by evidenceGate. The access email is org-scoped (no ACL metadata) but truth.json says accessGroups [field, access]; experiments/runners-core.ts KNOWN_UNDETECTABLE_LEAKS already lists 'email:f02-access-310@kalevanet.example' as a tolerated leak. Returning the barrier code to any requester widens that leak in E00 (demo split includes remote-power-access p2).
- Pirkko is in group 'field', and org-config gives field (and role Field Engineer) SITE_FACTS incl. site.access, so a site.access gap would list Pirkko via directory observability; Eino is available:false in people.json (eligibility 'unavailable'). 'Never Pirkko' needs a code-specific key observable only by group 'access' / role 'Site Access Coordinator', or a negative capability from the email; and naming Eino 'back on 1 Dec' needs availability-until data that people.json does not have.
- Renaming collision: EvidenceEnvelope.metadata.supersededBy already means 'a newer REVISION of the same source message' (ingest/import.ts:110) and commit.ts/case-view/context use it to drop refs and mark claims 'corrected'. Claim.supersededBy is a different concept; keep names distinct in code and docs.
- isLive() excludes everything but provisional|supported, and rebuildCase derives case.conditions, attempts, outcomes and gaps only from live claims. Marking a claim 'superseded' at commit time removes it from the persisted case, so an earlier `at` cannot see it any more unless point-in-time re-derives from claims (case.conditions is persisted, not time-aware) or 'superseded' is treated as live for rebuild and filtered at query time.
- buildCorpus indexes ALL caseful claim statements regardless of status, and loadCaseFacts.allClaims/hypothesisClaims/adviceClaims are not filtered by isLive; only case.conditions/attempts/outcomes are. A validity filter must be applied in loadCaseFacts and corpus (or via a time-aware EvidenceGate), not only in rebuildCase.
- investigate() always persists (`store.put('investigation', state)`) and investigationId = stableId('inv', problemId); Engine.investigate's problemId does not include `at`, so a point-in-time call would overwrite the live investigation and could start the question loop. Include `at` in the problem id and force allowQuestions false (or a non-persisting path) for past `at`. kt_get_context maps to getInvestigation, which returns the stored state without re-evaluation, so `at` there needs a re-run.
- Answers, observations and outcome reports are evidence with eventTime = clock now; an `at` earlier than the answer must exclude them (Observation.at, Answer.at), otherwise 'what was known at t' leaks later answers. priorAnswerConditions reuses answers across investigations by asset and key.
- Quiet hours: openQuestionIds counts queued AND delivered, so a quiet-queued question blocks that person (maxOpenQuestionsPerPerson 1) and the investigation (`request()` returns early on any queued/delivered).
