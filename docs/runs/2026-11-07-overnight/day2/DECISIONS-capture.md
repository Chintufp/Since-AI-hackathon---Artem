- D-B4-01 · Pasted threads are recognised by a pure sniffer, connectors/paste-thread.ts (detectPasteKind, parsePastedThread), in the order empty, JSON export with {messages}, e-mail, thread, note. Reason: the existing paste adapter stores one note with no speakers, so the rules extractor sees no claims by person. Reverse: route 'paste' straight to parsePaste again in memory/index.ts.
- D-B4-02 · E-mail means parseEmailHeaders finds a From, To, Subject or Message-ID header, not merely "a non-empty header block" as the brief says. Reason: 'Aarne: the link is up' parses as a header named 'aarne', so a plain two-speaker thread would have been taken for an e-mail. Reverse: test Object.keys(headers).length in detectPasteKind.
- D-B4-03 · Thread shapes: '[09:14] Name: text', '09:14 Name: text', 'Name  9:14 AM' or '[9:14 AM] Name' header lines followed by body lines, and plain 'Name: text' only with at least two different speakers and no timed line anywhere. Lines after a speaker line continue that message (multi-line messages keep their line breaks). A name is one to four capitalised words (lower-case particles such as 'van' allowed). Reason: a body line such as 'Did that at 9:20' must not open a new message, and inside a timed thread 'Note: counters zero' stays body text. Reverse: loosen NAME in paste-thread.ts.
- D-B4-04 · A 'Name:' line whose name is a common label (Problem, Steps, Status, Link, Note, Subject …, list LABELS in paste-thread.ts) is never a speaker, and free text before the first speaker line makes the whole paste a note. Reason: the brief forbids capturing a problem description as a thread; a labelled problem note ('Problem: … / Steps: …') would otherwise look like two speakers. Reverse: empty LABELS.
